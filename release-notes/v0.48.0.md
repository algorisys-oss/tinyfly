# v0.48.0

**Release Date:** 2026-09-12

Scroll animation becomes authorable. Closes the five items v0.47.0 shipped with
open, chief among them the editor preview that made the drivers developer-only.

## Scroll-scrub preview in the editor

Click **⇅ Scroll** in the preview header. A scrollable strip appears with a
trigger element in it; scrolling the strip scrubs the animation.

The part that matters: **this is not a simulation.** The preview attaches a real
`ScrollDriver` to a real scroll container and lets it measure real geometry. A
`start` / `end` pair tuned in the editor behaves identically on the page,
because it is the same code path. The panel prints the snippet that reproduces
what you are looking at, so there is no translation step between tuning and
shipping.

Controls: start/end trigger presets, scrub mode (exact or smoothed), runway
length above and below the trigger, a live progress percentage, and jump
buttons for top/middle/bottom. Normal playback pauses while the mode is on —
scroll position should be the only thing moving the playhead, as in production.

This needed one new primitive on the store, `syncPlayheadFromTimeline()`.
Drivers seek the `Timeline` directly, which is the correct boundary, but the
editor's readouts follow a signal — so something has to say "a driver moved us".

## Overlapping tracks are no longer silent

v0.47.0 documented a behaviour that had been undocumented for a long time: when
two tracks drive the same target and property over overlapping times, the
last-added one silently wins. The rule is fine — it is predictable — but the
silence is not: a discarded track looks like a bug in the animation.

The Tracks panel now warns. A banner counts the overlaps, each overridden track
is struck through with a ⚠, and its tooltip names the track that wins and why.

## Springs draw in the curve editor

Spring tracks previously showed as a span bar in the dope sheet and were skipped
by the graph editor entirely. They now draw a real curve, sampled from the same
`SpringSampler` the engine plays back — so the curve on screen is the motion
that runs, overshoot and all.

Their lanes are read-only and marked so (dashed line, `spring` badge): a
spring's shape comes from its parameters, not from points you can drag. The lane
is sized by `springRange`, which samples rather than reading `from`/`to`, so an
underdamped overshoot is not clipped out of view.

## Draggable shares the editor's snapping

`Draggable` had its own one-line grid rounding while the editor had a tested
`snapAxis` / `gridLinesFor` pair. The spec for this work said explicitly: reuse
it, do not fork it.

`snap.ts` moves to `src/interaction/snap.ts` — it was always pure, only its
location was editor-specific — and both callers now use it. `Draggable` gains
`snapLinesX` / `snapLinesY` for snapping to other elements' edges or guides, and
reports which line caught (via `snapLines` or the `onSnap` callback) so a host
can draw a guide.

Existing behaviour is preserved: `snapThreshold` defaults to half the grid size,
which puts every position within reach of a line, making `snap: n` behave
exactly like the rounding it replaced.

## Three scroll examples in the gallery

A new **Scroll** category: **Scroll Reveal** (fade and rise on entry),
**Scroll Parallax** (three layers drifting at different rates), and
**Scroll Progress Bar** (a fill scaled from its left edge).

The gallery loops them, because a card is too small to scroll in. Each therefore
carries a `driverSnippet` — shown under "Drive it from scroll" on the card —
giving the exact `ScrollDriver` or `VisibilityDriver` call that turns the same
timeline into a scroll-driven one.

### Test Coverage

- **1122 tests passing (1085 → 1122)** — 37 new
- Scroll-preview wiring: the driver scrubs the engine, the store mirrors it,
  trigger presets resolve, and an empty scene is harmless
- Spring curve sampling, including that it matches the engine's own values and
  that the lane range covers an underdamped overshoot
- `Draggable` snapping: grid parity with the old behaviour, edge lines,
  threshold, precedence, guide reporting, and bounds applied after snapping
- New structural tests over the gallery — which immediately caught an array hole
  from a stray comma, a defect that typechecks as `undefined` in the list

### A note on testing Solid memos

The store's new conflict accessors are `createMemo`s, and like the existing
`tracks()` / `duration()` memos they only recompute under the observer graph the
running app provides — not in a bare test, and not merely inside `createRoot`.
The tests assert against `timeline.findConflicts()` directly, which is the
convention this suite already documents for exactly this reason.

## Upgrade Notes

Upgrade from v0.47.0:

1. No data migration, no engine API change.
2. If you imported the snapping helpers directly, they moved:
   ```diff
   - import { snapAxis, gridLinesFor } from './editor/utils/snap'
   + import { snapAxis, gridLinesFor } from 'tinyfly/interaction'
   ```
3. `Draggable` snapping is unchanged for `snap: n`. If you want the old
   always-round behaviour alongside a custom `snapThreshold`, set the threshold
   to at least half the grid size.
