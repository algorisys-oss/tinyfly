# v0.50.1

**Release Date:** 2026-09-12

Three defects found by driving the real editor in a browser, including
pre-existing silent data loss.

Everything here was invisible to a 1,174-test suite. That is the point worth
taking from this release: each failure lived in a place unit tests structurally
cannot reach — a browser-only API, a parameter range the tests never used, and
CSS layout.

## Projects were not being saved

**Severity: data loss. Pre-existing — present since before v0.47.0, confirmed by
running v0.46.2.**

Project records go straight from a Solid store into `IDBObjectStore.put`. In the
browser those records are Proxies, and the structured clone algorithm rejects a
proxy outright with `DataCloneError`. The write was caught and logged, so the
editor carried on happily from memory.

The consequence: the only record that ever persisted was the **initial empty
project**. The moment the canvas had anything on it, every subsequent save was
dropped — and nobody found out until a reload, which restored the empty scene.

Fixed by `unwrap`-ing the record before writing, with a JSON round-trip as a
retry. The persisted format is JSON by contract (the LocalStorage backend stores
exactly that), so the fallback cannot lose anything.

**Why the tests missed it:** under Vitest's Node environment `createStore` does
not proxy at all — `state === unwrap(state)` — so the failure is not
reproducible there at any effort. The new regression test asserts the properties
the fix depends on and states that limitation in its own header rather than
implying coverage it does not have.

## Springs did not overshoot

A `scale: 0 → 1` spring reported "settles in 140 ms" and produced no bounce at
all, while the inspector's badge said it would overshoot. A badge that lies
about the motion is worse than no badge.

The rest thresholds were **absolute**, so a spring travelling 1 unit reached them
roughly 100× sooner than one travelling 100. The small spring was declared at
rest the instant it first touched its target — before any overshoot — and
clamped there.

Thresholds are now fractions of the spring's travel distance, which makes
settling depend on the spring's parameters rather than on the units of whatever
property it happens to drive. The same spring now settles in 854 ms and peaks at
1.28, and `scale: 0→1` and `x: 0→100` settle at identical times.

**Why the tests missed it:** every existing spring test used `from: 0, to: 100`.
Every spring *preset* uses `0 → 1`. The new `spring-scale.test.ts` covers small
magnitudes, asserts scale invariance directly, and checks that the reported
settle window actually contains the bounce.

## The scroll preview was invisible

Stacked below the stage, the panel was clipped away entirely by the preview
panel's `overflow: hidden` — the timeline splitter owns most of that column's
height, leaving ~50px. Worse, before the clipping took effect the panel pushed
the stage off-screen, so you could not see the animation you were scrubbing.

It now sits **beside** the stage as a narrow column, which costs no vertical
height at all; the stage simply narrows. The code snippet is collapsed behind a
disclosure for the same reason.

**Why the tests missed it:** layout is not something this suite can assert.

## What browser testing confirmed working

Everything else verified end to end: spring presets apply and build the right
track kinds; the spring inspector's sliders drive the engine live (damping 11→4
moved settle 854→2300 ms and the scene auto-extended 2.000→2.300s, proving the
sampler is rebuilt rather than mutated); the overlapping-track banner, ⚠ markers
and tooltips; spring curves drawing as a proper damped oscillation in the graph
editor; scroll scrubbing mapping 0→100% onto 0→2.300s; and all three scroll
gallery examples with their driver snippets.

## Upgrade Notes

Upgrade from v0.50.0:

1. **`restDelta` and `restSpeed` changed meaning** — they are now fractions of
   the spring's travel distance rather than absolute values, and `restSpeed`
   defaults to 0.1. Springs using the defaults will settle later than before and
   will now actually show their overshoot. If you set either explicitly, re-read
   them as fractions.
2. No data migration. Projects that failed to save will simply start saving.
