# v0.47.0

**Release Date:** 2026-09-12

Closes the GSAP gap: scroll-driven playback, deterministic springs, a pointer
interaction layer, FLIP, a WebGL adapter, and a GSAP-flavoured authoring API —
all of it compiling to ordinary tinyfly JSON.

This is the largest feature release so far. It started as a question — "is our
API GSAP-compatible?" — and the honest answer was no, and only partly similar.
Rather than paper over that, the gaps were specified (Phases 25 and 26 in
[todo.md](../todo.md)) and then built.

## The organising idea

The engine is a pure function of time. Almost everything GSAP does that tinyfly
could not falls into one of three shapes, and each has a home that leaves the
engine's principles intact:

| Shape | Where it goes | Examples |
|---|---|---|
| Decides *what time* to pass in | A **driver** | Scroll, visibility, drag-to-scrub |
| Computes concrete values ahead of time | An **authoring-time compiler** | FLIP, relative/random values, stagger baking |
| Extends the track model narrowly | An **engine feature** | Spring tracks, runtime stagger |

Anything fitting none of the three is in the "deliberately rejected" list, with
its reasoning recorded so it is not relitigated: runtime function values,
`repeatRefresh`, implicit `getComputedStyle` start values, `overwrite: 'auto'`,
and a plugin architecture.

## Scroll-driven playback

`ScrollDriver` scrubs a timeline against scroll position; `VisibilityDriver`
plays one when its trigger enters the viewport. Neither is a special kind of
timeline — they just call `seek()`, so every animation you already have can be
scroll-driven without changing it.

```ts
import { ScrollDriver, VisibilityDriver } from 'tinyfly/drivers'

new VisibilityDriver({ timeline, trigger, behaviour: 'once' }).start()

new ScrollDriver({
  timeline, trigger,
  start: 'top bottom', end: 'bottom top',
  scrub: true,
}).start()
```

GSAP-style trigger strings are supported (`'top bottom'`, `'center center'`,
`'top top+=500'`, `'25% 75%'`, bare pixel offsets). The geometry lives in a pure
`scrollProgress()` that is unit-tested without a browser; the driver is a thin
DOM shell around it.

**Pinning is deliberately absent.** It mutates page layout, which is where most
of ScrollTrigger's complexity lives, and `position: sticky` covers the common
cases — the recipe is in [docs/scroll-animation.md](../docs/scroll-animation.md).

## Deterministic springs

A spring is now a track kind. The interesting part is that it is physical *and*
deterministic *and* serializable at the same time:

```ts
timeline.addTrack({
  id: 'pop', target: 'box', property: 'scale',
  kind: 'spring',
  spring: { from: 0, to: 1, stiffness: 200, damping: 12 },
})
```

The trap this avoids: a naive spring integrates from the previous frame's state,
which makes output depend on frame rate and on which direction you scrubbed
from. Instead the simulation always runs forward from rest at t=0 at a fixed 1ms
substep, memoised so scrubbing stays cheap. Seeking backwards to 300ms gives the
identical value as playing forwards to it, and two runs are byte-identical.

Because the animation is the *parameters*, a spring track exports like any other
track. Export formats that only understand keyframes (CSS, Lottie) bake it
automatically.

## Interaction layer

```ts
import { Observer, Draggable } from 'tinyfly/interaction'

new Draggable({ target: el, mode: 'scrub', timeline, scrubDistance: 500 }).start()
new Draggable({ target: el, axis: 'x', bounds: { minX: 0, maxX: 300 }, snap: 25 }).start()
```

`Observer` normalises pointer, touch and wheel into one delta+velocity shape.
`Draggable` has two modes, and the difference is documented because it matters:
`scrub` drives a timeline (nothing new is stored), while `move` reports positions
for the caller to apply and has **no serializable representation** — a dragged
position is not part of an animation document.

## FLIP, without live layout reads in the engine

```ts
import { flip } from 'tinyfly/adapters/dom'

const tracks = flip([{ name: 'card', element: cardEl }], () => {
  container.classList.add('grid-layout')
})
```

Measurement happens in the DOM layer at authoring time and emits ordinary
two-keyframe tracks. The trade-off is stated plainly in the module: the JSON is a
snapshot of one specific layout change, so recompute it when the layout it was
measured against changes.

## GSAP-flavoured authoring

```ts
import { timeline, quickPlay } from 'tinyfly/gsap-compat'

const tl = timeline()
tl.fromTo('box', { x: 0, opacity: 0 }, { x: 200, opacity: 1, duration: 1, ease: 'power2.out' })
tl.to(['l1', 'l2', 'l3'], { y: 0, duration: 0.5, stagger: { each: 0.08, from: 'center' } }, '-=0.25')

quickPlay({ timeline: tl.timeline, targets: { box: '#box', l1: '#l1', l2: '#l2', l3: '#l3' } })
```

**Familiar, not compatible** — GSAP code will not run unchanged, and the docs say
so in the first paragraph. What it is: a desugarer. Every call compiles to plain
track data, so anything authored through it opens in the editor and exports as
normal JSON. Position parameters (`'+='`, `'-='`, `'<'`, `'>'`, labels), stagger,
ease names, `repeat`/`yoyo`/`timeScale`, and nested timelines are all supported.

The one behavioural difference worth knowing: GSAP's `to()` reads the live DOM to
find its start value. tinyfly cannot — that is the implicit browser state
determinism rules out — so a documented four-step resolution chain is used
instead, and the facade *warns* when it reaches the static-default step, which is
where GSAP users get surprised.

`quickPlay` is worth having on its own: it replaces the dozen lines of
`DOMAdapter` + rAF boilerplate every hand-written example starts with.

## Engine additions

- **Runtime stagger** — one track fans across many targets (`each` / `amount` /
  `from: start|end|center|edges|index`). A test asserts it produces values
  identical to baking N separate tracks.
- **Track scheduling** — per-track `delay` and `endDelay`.
- **`repeatDelay`** — a pause between loop iterations.
- **Track queries** — `getTracks(filter)`, `removeTracks(filter)`,
  `getTrackSpan(id)`. This is the principled equivalent of GSAP's per-tween
  `kill()`: we have no live tween objects, so a tween is addressed by describing
  the tracks it produced.
- **`findConflicts()`** — surfaces a previously undocumented behaviour: when two
  tracks drive the same target+property over overlapping times, the
  *last-added* one silently wins. The rule is kept (it is predictable) but is now
  documented in `getStateAtTime` and detectable. Wiring an editor warning to it
  is still outstanding.
- **Compile-time values** — `"+=100"` and `"random(-50, 50)"` resolve when the
  timeline is built, from a recorded seed, so the JSON holds plain numbers and
  replays identically. This is the deterministic answer to GSAP's runtime
  function values.
- **Baking** — `bakeSpringTrack`, `bakeEasing`, `simplifyKeyframes`.

## Adapters

- **`transformOrigin`** as interpolatable `originX`/`originY` percentages, across
  DOM, SVG and Canvas. Canvas needed it most: it had no pivot concept at all, so
  rotate and scale always pivoted at the element's own centre.
- **`perspective`** on DOM and SVG, emitted first in the transform list so it
  affects the 3D functions after it.
- **WebGL adapter** (`src/adapters/webgl/`) — CLAUDE.md has listed WebGL as a
  supported target for some time with no adapter behind it. This is a minimal
  one: quad-per-element with transform, opacity and tint. Its limits are stated
  in the module — no paths, text or gradients.

## Two bugs the new tests caught

Both are worth recording, because both were principle violations rather than
ordinary slips:

- The compat facade defaulted its timeline id to `Date.now()`, so **the same
  script compiled to different JSON on every run**. Caught by the "compiles
  identically" test that exists precisely to check that.
- Position parameters were parsed as milliseconds when GSAP means **seconds**, so
  `'-=0.25'` moved a tween back by a quarter of a millisecond. Fixed by putting
  the seconds→ms conversion in exactly one place (a `scale` on `PositionContext`).

### Test Coverage

- **1085 tests passing (731 → 1085)** — 354 new
- Spring determinism: same values regardless of sampling order or density
- Runtime stagger proven identical to the baked equivalent
- Compat output: golden fixture, JSON round-trip, and byte-identical recompiles
- Scroll geometry: monotonicity, clamping, degenerate ranges, nested scrollers
- Drivers and interaction tested against faked browser APIs (no DOM required)

### A note on the type change

`AnyTrack` now includes `SpringTrack`, which has no `keyframes`. TypeScript
surfaced every place in the editor that assumed otherwise — about 60 call sites.
Each was narrowed with the new `hasKeyframes()` guard rather than cast, and the
timeline view now draws spring tracks as a span bar instead of pretending they
have keyframes to drag.

## Upgrade Notes

Upgrade from v0.46.2:

1. No data migration. Existing animation JSON loads unchanged.
2. `TimelineDefinition.tracks` is typed `AnyTrack[]` rather than `Track[]`. If
   you read `.keyframes` off a track in TypeScript, narrow it first:
   ```ts
   import { hasKeyframes } from 'tinyfly'
   if (hasKeyframes(track)) { /* track.keyframes is available */ }
   ```
3. Three new optional entry points, none of which affect existing bundles:
   `tinyfly/drivers`, `tinyfly/interaction`, `tinyfly/gsap-compat`. Build them
   with `npm run build:addons` (now part of `build:libs`).
