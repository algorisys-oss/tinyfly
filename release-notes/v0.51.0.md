# v0.51.0

**Release Date:** 2026-09-12

First performance measurement against GSAP, and two optimisations it found.

Phase 27C.2. Until now, every claim about tinyfly's performance rested on bundle
size. Now there are numbers, including the ones that do not flatter us.

## The headline

**GSAP is about 3× faster per frame at realistic sizes.**

| elements | tinyfly | GSAP | ratio | tinyfly headroom @60fps |
|---:|---:|---:|---:|---:|
| 100 | 0.60 ms | 0.20 ms | 3.0× | 27.8× |
| 500 | 1.70 ms | 0.70 ms | 2.4× | 9.8× |
| 1,000 | 3.00 ms | 1.10 ms | 2.7× | 5.6× |
| 2,000 | 6.00 ms | 2.10 ms | 2.9× | 2.8× |
| 4,000 | 15.30 ms | 3.20 ms | 4.8× | 1.1× |

Both libraries driven manually from the same loop — GSAP's ticker put to sleep
and its root advanced via `gsap.updateRoot` — so the comparison is symmetric
rather than measuring our loop against their scheduler.

The honest reading: this is a real gap, and at the same time not a problem for
normal pages. 5.6× headroom at 1,000 animated elements is far past what most
sites do. It starts to matter at 4,000+, where we are at the frame budget and
GSAP still has 5× spare.

The ratio is roughly flat from 100 to 2,000, which means a **constant factor
rather than a worse algorithm** — the encouraging reading, because constant
factors are the kind you can chip away at.

## Where the time actually goes

| elements | engine | adapter | engine share |
|---:|---:|---:|---:|
| 1,000 | 0.70 ms | 2.30 ms | 23% |
| 4,000 | 2.20 ms | 6.00 ms | 27% |

**The DOM adapter is ~75% of the cost. Interpolation is ~25%.**

That is the most useful thing these benchmarks produced. The engine — the part
the project's principles are actually about — is not the bottleneck. Roughly
12,000 keyframe tracks fit inside a single 60 fps frame when you measure
evaluation alone.

Part of the adapter's cost is structural: the engine produces a state map and
the adapter reads it back and composes strings, where GSAP writes straight to
the element. That indirection is the adapter architecture, not an oversight, so
the remaining work is optimising within it.

## Two optimisations

**Colour interpolation re-parsed its endpoints on every frame**, and
reallocated its `isHex`/`isRgb`/`isRgba` predicates on every call. Endpoints are
keyframe values — the same few strings for the life of an animation — so they
are now memoised (bounded at 512 entries) and the helpers hoisted.

Measured within a single run to control for machine state, a colour track went
from **2.44× the cost of a numeric track to 1.35×**.

**The DOM adapter allocated three objects and an array per element per frame**
for origins, clipping and filters — whether or not the element used any of them,
which most do not. About a million throwaway objects a second at 4,000 elements.
Now allocated lazily: adapter cost at 4,000 elements went **7.10 ms → 6.00 ms**.

## One optimisation that made things worse

Worth recording, because the instinct was strong and wrong.

Caching the last composed transform string per element, to skip an unchanged
`style.transform` write, **slowed the adapter down**: 2.40 ms → 2.80 ms at 1,000
elements. In a running animation every transform changes every frame, so the
cache never hits and each element pays an extra WeakMap get *and* set for
nothing.

Reverted, with the reasoning left in a comment at the write site so nobody
re-derives it. It would only pay off for tracks that have already settled, which
is not the case worth optimising for.

## Also corrected

An earlier, less rigorous measurement (in v0.50.0) reported that runtime stagger
and baked stagger evaluate at parity, and concluded the feature was justified on
file size alone. With proper warm-up and a median of 1,000 samples, runtime
stagger evaluates about **2× faster** at 1,000 targets. The file-size argument
still stands on its own; speed is now a second point in its favour rather than a
wash.

### Test Coverage

- 1,191 tests passing, unchanged — both optimisations are behaviour-preserving
  and covered by the existing interpolation and adapter suites.

### Caveats, stated plainly

One machine, one browser, one workload shape. Ratios travel between machines;
absolute numbers do not. Nothing here measures memory, startup cost, or
Firefox/WebKit — the last is blocked on 27C.1, which remains the more important
piece of work.
